## Einleitung

Hey! Freitag, dreiundzwanzig Uhr, ich sitze mit dem Laptop auf den Knien und versuche eine Frage zu beantworten: warum sagt meine Browser-Erweiterung der Seite, dass keine Passkeys verfügbar sind, obwohl ich in der Konsole klar sehe, dass ich sie abfange. Das ist nur einer von vielen Abenden an einem Nebenprojekt, das ich schon eine Weile mit mir herumschleppe: eine Web-App plus eine Browser-Erweiterung, die als persönlicher Passkey-Vault fungieren soll. So etwas wie Bitwarden oder 1Password, nur schlanker und auf meine Bedürfnisse zugeschnitten, weil ich endlich verstehen wollte, wie das unter der Haube tatsächlich funktioniert, statt einfach nur auf "mit Passkey anmelden" zu klicken und darauf zu vertrauen, dass jemand anderes das schon richtig gemacht hat. Ein Grund, der mich überhaupt erst überzeugt hat, hier Zeit reinzustecken: anders als SMS-Codes oder OTP-Apps funktionieren Passkeys auch offline, weil die gesamte Schlüsselprüfung lokal auf dem Gerät passiert.

Ich habe mit der Web-App angefangen, weil das der naheliegende Startpunkt war, und dachte, die Erweiterung wäre dann nur noch eine Wochenend-Ergänzung. Drei Abende später saß ich immer noch an derselben Stelle, weil kein Tutorial mir eine Sache klar gesagt hat: eine Browser-Erweiterung hat keinen offiziellen Haken, um in das einzugreifen, was die App bereits tat. Man muss das umgehen. Und diese Umgehung hat Sicherheitskonsequenzen, über die man besser nachdenkt, bevor man sie in Produktion schickt, und nicht erst danach, wie ich.

Das bekommst du aus diesem Beitrag, so wie dieses Projekt tatsächlich Schritt für Schritt entstanden ist:

1. **woher die Web-App kam und warum ich wollte, dass meine Erweiterung das übernimmt statt des systemeigenen Authenticators**,
2. **wie die Erweiterung am Ende diese Aufrufe abgefangen hat, obwohl es dafür keine dedizierte API gibt**,
3. **wo mich der Kompromiss zwischen Komfort und Sicherheit erwischt hat**, denn der ganze Sinn von Passkeys ist ein nicht exportierbarer Schlüssel, und ich baue etwas, das per Definition genau diesen Schlüssel zwischen Geräten verschieben will.

Das ist kein fertiges Produkt und ich werde nicht so tun, als hätte ich schon alles im Griff. Das ist eine Momentaufnahme von der Mitte des Wegs, genau an dem Punkt, an dem beide Teile, App und Erweiterung, schon etwas zusammen können, ich aber immer noch mit mir selbst streite, ob das eine gute Idee ist.

## Die Web-App wollte schon Passkeys, bevor die Erweiterung überhaupt etwas konnte

Ich habe mit dem Backend der Web-App angefangen, weil es ohne das nichts abzufangen gibt: es stellt die Challenge aus, hält die `rp.id` und prüft die Signatur beim Login. Die Registrierung eines Passkeys sieht von der Seite aus ungefähr so aus:

```js
const credential = await navigator.credentials.create({
  publicKey: {
    challenge: new Uint8Array(32), // zufällige Serverdaten, gegen Replay-Angriffe
    rp: { name: "mein-service.de", id: "mein-service.de" },
    user: {
      id: new TextEncoder().encode(userId),
      name: "bartek@beispiel.de",
      displayName: "Bartek",
    },
    pubKeyCredParams: [{ type: "public-key", alg: -7 }], // -7 ist ES256
    authenticatorSelection: { residentKey: "required", userVerification: "preferred" },
  },
});
```

Ich habe die Doku gelesen, genickt, gedacht "na klar, das ist doch einfach", und tatsächlich hatte ich das Backend an einem Abend fertig: `rp.id` muss zu der Domain passen, von der der Aufruf kommt, und das überwacht der Browser, nicht der Server. Genau deshalb bekommt eine gefälschte Seite wie `mein-service-de.ru` physisch keine gültige Signatur, selbst wenn der Nutzer alles wegklickt, was ihm entgegenspringt. Die Login-Tests mit Touch ID liefen durch, die App funktionierte.

Nur dass das alles normalerweise vom "plattformeigenen Authenticator" der App übernommen wurde, also Touch ID, Windows Hello oder dem in den Browser eingebauten Passwortmanager. Der private Schlüssel hat diesen Bereich nie verlassen. Ich wollte, dass stattdessen meine Erweiterung das übernimmt, damit der ganze Vault an einem Ort lebt, den ich selbst kontrolliere. Genau da hörte die App auf, eine einfache Aufgabe zu sein, und die eigentliche Arbeit begann.

## Die Erweiterung hat keine WebAuthn-API, also muss man sie austricksen

Ich habe lange nach so etwas wie `chrome.webAuthn` in Manifest V3 gesucht. So etwas gibt es nicht. Browser-Erweiterungen haben keinen privilegierten Zugriff auf die WebAuthn-Schicht des Betriebssystems, Punkt. Was echte Passwortmanager machen (ich habe nachgeschaut, wie Bitwardens technische Doku das beschreibt, weil sie ziemlich offen über ihre Architektur sind), ist, `navigator.credentials` auf Seitenebene auszutauschen, bevor irgendein Skript der Seite selbst darauf zugreifen kann, genau an der Stelle, an der das Backend meiner App einen Aufruf von einem "normalen" Authenticator erwartet.

In Manifest V3 macht man das mit `world: "MAIN"` im Content Script, also Code, der direkt in den Kontext der Seite injiziert wird, statt in die isolierte Welt der Erweiterung:

```json
{
  "content_scripts": [
    {
      "matches": ["<all_urls>"],
      "js": ["inject.js"],
      "world": "MAIN",
      "run_at": "document_start"
    }
  ]
}
```

In `inject.js` tausche ich die Methoden gegen meine eigenen aus, die über `window.postMessage` mit dem Content Script in der isolierten Welt reden, und das wiederum über `chrome.runtime.sendMessage` mit dem Background Service Worker, wo die eigentliche Vault-Logik sitzt:

```js
const originalCreate = navigator.credentials.create.bind(navigator.credentials);

navigator.credentials.create = async function (options) {
  if (!options?.publicKey) return originalCreate(options);
  const response = await requestFromExtension("create", options.publicKey);
  return response ?? originalCreate(options);
};
```

Das Timing ist hier gnadenlos. Wenn du `run_at` auf `document_end` statt `document_start` setzt, schafft es die Seite, sich vorher eine Referenz auf das originale `navigator.credentials` zu sichern, und dein Austausch bringt nichts, weil die Seite trotzdem den alten Handle benutzt. Dafür habe ich einen ganzen Abend verbraten, bevor ich verstanden habe, dass die Injektionsreihenfolge kein Detail ist, sondern eine zwingende Voraussetzung.

Zweite Falle, und das ist die, die mich bis dreiundzwanzig Uhr an diesem Freitag wachgehalten hat: man muss auch `PublicKeyCredential.isConditionalMediationAvailable()` austauschen, weil viele Seiten erst dieses Flag prüfen, bevor sie überhaupt eine UI zum Passkey-Login zeigen. Vergisst du diese eine Methode, bekommt dein Vault nie eine Chance, weil die Seite entscheidet, dass Passkeys nicht verfügbar sind, obwohl dein Abfangen einwandfrei funktioniert. Ich habe eine gute halbe Stunde vor mich hin geflucht, bevor mir klar wurde, dass das Problem nicht in meinem Code lag, sondern in einer Methode, die ich schlicht vergessen hatte.

## Wo mich der Kompromiss erwischt hat: der Schlüssel, der nie hätte rausgehen sollen

Die Erweiterung fing schon Aufrufe ab, das Backend der App akzeptierte sie schon, also dachte ich, das Schlimmste läge hinter mir. Da wurde mir klar, was ich eigentlich gebaut hatte: der ganze Sinn von WebAuthn basiert darauf, dass der private Schlüssel nicht exportierbar ist und das Gerät oder den Hardware-Authenticator nie verlässt. Daher kommt die Resistenz gegen Phishing und Datendiebstahl.

Aber ich baue einen Vault, dessen ganzer Sinn es ist, dass derselbe Passkey auf Laptop und Handy funktioniert, also müssen Web-App und Erweiterung auf beiden Geräten denselben Schlüssel sehen. Der Schlüssel muss also irgendwie synchronisiert werden. In der Praxis heißt das: ich generiere ein Schlüsselpaar über WebCrypto, aber statt `extractable: false` (was die Spezifikation empfiehlt und was ein echter Hardware-Authenticator tut), muss ich `extractable: true` verwenden, um den Schlüssel verschlüsseln und in meine eigene Sync-Datenbank schieben zu können, dieselbe, auf die auch das Backend der App zugreift:

```js
const keyPair = await crypto.subtle.generateKey(
  { name: "ECDSA", namedCurve: "P-256" },
  true, // extractable: true, sonst ist Synchronisation unmöglich
  ["sign", "verify"]
);
```

Das ist, soweit ich das aus ihren öffentlichen Materialien verstehe, genau derselbe Kompromiss, den Bitwarden und 1Password bei ihren Passkey-Implementierungen eingehen: sie nennen das "software-backed passkeys" im Gegensatz zu "hardware-backed", und schreiben ausdrücklich, dass das ein niedrigeres Sicherheitsniveau ist als ein Schlüssel, der in einer Secure Enclave oder einem TPM eingeschlossen ist. Der Komfort der Synchronisation kostet einen echten Rückgang der Garantien, die die Spezifikation eigentlich verspricht. Das ist kein Implementierungsfehler, das ist eine fundamentale architektonische Entscheidung, und wer "Passkeys in der Cloud" als identisch zu einem Hardware-Schlüssel bewirbt, lügt ein bisschen durch Auslassung.

Mein aktueller Plan ist, den privaten Schlüssel lokal mit einem aus dem Master-Passwort abgeleiteten Schlüssel zu verschlüsseln (so etwas wie PBKDF2 oder Argon2 zum Stretching), bevor irgendetwas in die Synchronisation geht, damit der Server den Schlüssel nie im Klartext sieht. Aber das bleibt trotzdem eine Software-Lösung mit dem ganzen Gepäck, das dazugehört: wenn jemand das Master-Passwort knackt und Zugriff auf die verschlüsselte Datenbank hat, ist das Spiel vorbei. Ein Hardware-Key hat dieses Problem nicht, weil es dort gar nichts gibt, was man aus der Ferne "wiederherstellen" könnte.

## FAQ

**Haben Browser eine offizielle API für Passwortmanager, um WebAuthn zu handhaben?**
Es gibt keine dedizierte API der Klasse `chrome.webAuthn` für Erweiterungen. Alle mir bekannten Passwortmanager machen dasselbe wie oben beschrieben: sie tauschen `navigator.credentials` über ein injiziertes Skript aus, das in der Hauptwelt der Seite läuft.

**Was ist der Unterschied zwischen einem "software-backed" und einem "hardware-backed" Passkey?**
Hardware-backed bedeutet, der private Schlüssel entsteht und lebt ausschließlich in einem dedizierten Modul (Secure Enclave, TPM, Hardware-Key) und lässt sich physisch nicht exportieren. Software-backed bedeutet, der Schlüssel existiert als verschlüsselte Daten, die man theoretisch wiederherstellen könnte, wenn jemand die Verschlüsselung oder das Master-Passwort knackt. Letzteres ist bequemer für die Synchronisation, hat aber ein schwächeres Bedrohungsmodell.

**Warum ist `run_at: document_start` so wichtig?**
Weil die Seite sich direkt nach dem Laden eine Referenz auf das originale `navigator.credentials` sichern kann, bevor die Erweiterung überhaupt etwas austauschen konnte. Kommt der Austausch zu spät, benutzt die Seite trotzdem den alten Handle, und dein Abfangen greift nie.

**Planst du, das zu veröffentlichen oder den Code freizugeben?**
Aktuell ist das ein Projekt für den Eigenbedarf und zum Lernen, also gibt es noch kein öffentliches Repo und keinen Termin. Wenn es einen Stand erreicht, den ich für stabil genug halte, dass ihn jemand anderes sicher nutzen kann, schreibe ich definitiv einen eigenen Beitrag darüber.

## Zusammenfassung

Das war's für heute! Kurz zusammengefasst: ich habe eine Web-App, die einen normalen WebAuthn-Flow bereitstellt, und eine Erweiterung, die sich dort einklinkt, indem sie `navigator.credentials` in der Hauptwelt der Seite austauscht, mit einem gnadenlosen Injektions-Timing. Und wenn du willst, dass diese beiden Teile Schlüssel zwischen Geräten synchronisieren, musst du bewusst vom Modell "Schlüssel verlässt das Gerät nie" zum Modell "Schlüssel ist verschlüsselt, aber theoretisch wiederherstellbar" wechseln, und es gibt keine magische Lösung, die dir beides gleichzeitig gibt.

Und jetzt die Ironie an der ganzen Sache: ich habe das gebaut, weil ich die Abhängigkeit von Passwortmanagern anderer Firmen loswerden und etwas Eigenes, von mir Kontrolliertes haben wollte, App und Erweiterung zusammen. Nach drei Abenden komme ich zu dem Schluss, dass der einzige Weg, meinen Vault so sicher wie Bitwarden zu machen, im Grunde darin besteht, die halbe architektonische Entscheidung, die Bitwarden schon getroffen hat, neu zu schreiben, nur schlechter, weil ich allein bin und nur nach Feierabend Zeit habe. Unabhängigkeit bedeutet manchmal einfach, dieselben Kompromisse neu zu entdecken, die jemand anderes schon längst entdeckt und in seiner technischen Doku aufgeschrieben hat lol.
