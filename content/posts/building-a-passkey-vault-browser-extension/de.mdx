## Einleitung

Hallo! Freitag, dreiundzwanzig Uhr, ich sitze mit dem Laptop auf den Knien und versuche, eine Frage zu beantworten: Warum sagt meine Browser-Erweiterung der Seite, dass keine Passkeys verfügbar sind, obwohl ich in der Konsole deutlich sehe, dass ich sie abfange. Das ist nur einer von vielen Abenden an einem Nebenprojekt, das ich schon eine Weile mit mir herumschleppe: eine Webanwendung plus eine Browser-Erweiterung, die als persönlicher Passkey-Vault fungieren soll. So etwas wie Bitwarden oder 1Password, nur schlanker und auf meine Bedürfnisse zugeschnitten, weil ich endlich verstehen wollte, wie das Ganze unter der Haube funktioniert, statt einfach nur auf "mit Passkey anmelden" zu klicken und darauf zu vertrauen, dass jemand das schon richtig gemacht hat.

Die WebAuthn-Dokumentation sieht nach zwei Funktionen aus, mehr nicht: `navigator.credentials.create()` und `navigator.credentials.get()`. Ich habe es gelesen. Genickt. Gedacht "na klar, das ist einfach". Drei Abende später saß ich immer noch an derselben Stelle fest, weil kein Tutorial mir eine Sache klar gesagt hatte: Eine Browser-Erweiterung hat keinen offiziellen Haken, um diese Aufrufe abzufangen. Man muss es umgehen. Und dieser Workaround hat Sicherheitskonsequenzen, über die man besser nachdenkt, bevor man ihn in Produktion schickt, und nicht erst danach, so wie ich.

Du bekommst drei Dinge aus diesem Beitrag:

1. **wie WebAuthn unter der Haube wirklich aussieht**, also was zwischen dem Klick auf "mit Passkey anmelden" und dem Speichern des Schlüssels passiert,
2. **wie eine Browser-Erweiterung sich da einklinken kann**, obwohl es keine dedizierte API dafür gibt,
3. **wo mich der Kompromiss zwischen Komfort und Sicherheit gebissen hat**, denn der ganze Sinn von Passkeys ist ein nicht exportierbarer Schlüssel, und ich baue etwas, das diesen Schlüssel per Definition zwischen Geräten verschieben will.

Das ist kein fertiges Produkt, und ich werde nicht so tun, als hätte ich schon alles im Griff. Das ist eine Momentaufnahme mitten auf dem Weg, genau an dem Punkt, an dem die Erweiterung schon etwas kann, ich aber noch mit mir selbst streite, ob das eine gute Idee ist.

## Wie WebAuthn funktioniert, wenn man eine Ebene tiefer geht

Bevor du die Erweiterung anfasst, lohnt es sich zu verstehen, was auf Seitenebene passiert. Die Registrierung eines Passkeys sieht aus Sicht des JavaScripts der Seite ungefähr so aus:

```js
const credential = await navigator.credentials.create({
  publicKey: {
    challenge: new Uint8Array(32), // Zufallsdaten vom Server, gegen Replay-Angriffe
    rp: { name: "mein-service.de", id: "mein-service.de" },
    user: {
      id: new TextEncoder().encode(userId),
      name: "bartek@beispiel.de",
      displayName: "Bartek",
    },
    pubKeyCredParams: [{ type: "public-key", alg: -7 }], // -7 ist ES256
    authenticatorSelection: { residentKey: "required", userVerification: "preferred" },
  },
});
```

Was in `credential.response` zurückkommt, ist eine `AuthenticatorAttestationResponse`. Darin steckt `attestationObject`, das CBOR-kodiert ist und `authData` enthält (unter anderem den öffentlichen Schlüssel und die Credential-ID) sowie `clientDataJSON`, worin der Origin der Seite und die Challenge stecken, signiert so, dass der Server verifizieren kann, dass wirklich diese Seite gefragt hat.

Die Sache, die leicht übersehen wird: `rp.id` muss eine Domain sein, die zum Aufrufer passt, und das überwacht der Browser, nicht der Server. Das ist die Grundlage dafür, dass Passkeys phishing-resistent sind: Der private Schlüssel ist mathematisch an einen bestimmten Origin gebunden, sodass eine gefälschte Seite wie `mein-service-de.ru` physisch keine gültige Signatur bekommen kann, selbst wenn der Nutzer alles anklickt, was auftaucht.

Und jetzt der Kern der Sache: Normalerweise übernimmt das alles ein "Plattform-Authenticator", also Touch ID, Windows Hello, ein Hardware-Schlüssel oder der im Browser eingebaute Passwort-Manager. Der private Schlüssel verlässt ihn nie. Ich will, dass stattdessen meine Erweiterung das übernimmt. Und da fängt der Spaß an.

## Die Erweiterung hat keine WebAuthn-API, also muss man sie austricksen

Ich habe lange nach so etwas wie `chrome.webAuthn` oder Ähnlichem in Manifest V3 gesucht. Es gibt so etwas nicht. Null. Browser-Erweiterungen haben keinen privilegierten Zugriff auf die WebAuthn-Schicht des Betriebssystems, Punkt. Was echte Passwort-Manager tun (ich habe nachgeschaut, wie Bitwardens technische Dokumentation das beschreibt, weil sie ziemlich offen über ihre Architektur sind), ist, `navigator.credentials` auf Seitenebene auszutauschen, bevor irgendein Skript dieser Seite die Chance hat, darauf zuzugreifen.

In Manifest V3 macht man das mit `world: "MAIN"` im Content-Script, also Code, der direkt in den Kontext der Seite injiziert wird und nicht in die isolierte Welt der Erweiterung:

```json
{
  "content_scripts": [
    {
      "matches": ["<all_urls>"],
      "js": ["inject.js"],
      "world": "MAIN",
      "run_at": "document_start"
    }
  ]
}
```

In `inject.js` ersetze ich die Methoden durch meine eigenen, die über `window.postMessage` mit dem Content-Script in der isolierten Welt reden, das dann über `chrome.runtime.sendMessage` mit dem Background-Service-Worker spricht, wo die eigentliche Vault-Logik sitzt:

```js
const originalCreate = navigator.credentials.create.bind(navigator.credentials);

navigator.credentials.create = async function (options) {
  if (!options?.publicKey) return originalCreate(options);
  const response = await requestFromExtension("create", options.publicKey);
  return response ?? originalCreate(options);
};
```

Das Timing ist hier absolut. Wenn du `run_at` auf `document_end` statt `document_start` setzt, hat die Seite sich schon eine Referenz auf das originale `navigator.credentials` in ihrem eigenen Code gesichert, bevor du es austauschen kannst, und dein Ersatz macht dann nichts, weil die Seite ohnehin am alten Handle hängt. Ich habe darüber einen ganzen Abend verbraten, bevor mir klar wurde, dass die Reihenfolge der Injektion kein Detail ist, sondern eine harte Voraussetzung.

Die zweite Falle, die mich bis dreiundzwanzig Uhr an jenem Freitag wach gehalten hat: Man muss außerdem `PublicKeyCredential.isConditionalMediationAvailable()` ersetzen, weil viele Seiten zuerst dieses Flag prüfen, bevor sie überhaupt eine UI zum Anmelden per Passkey zeigen. Vergisst du diese eine Methode, bekommt dein Vault nie eine Chance, weil die Seite entscheidet, dass keine Passkeys verfügbar sind, obwohl dein Abfangen einwandfrei funktioniert. Ich habe eine gute halbe Stunde vor mich hin geflucht, bevor mir klar wurde, dass das Problem nicht in meinem Code lag, sondern in einer Methode, die ich komplett vergessen hatte.

## Wo mich der Kompromiss gebissen hat: der Schlüssel, der nie rausgehen sollte

Jetzt komme ich zu der Sache, die mich wirklich länger aufgehalten hat. Der ganze Sinn von WebAuthn beruht darauf, dass der private Schlüssel nicht exportierbar ist und nie das Gerät oder den Hardware-Authenticator verlässt. Daher kommt die Resistenz gegen Phishing und Datendiebstahl.

Aber ich baue einen Vault, dessen ganzer Sinn darin besteht, dass derselbe Passkey sowohl auf dem Laptop als auch auf dem Handy funktioniert. Das heißt, der Schlüssel muss irgendwie synchronisiert werden. In der Praxis bedeutet das, ich generiere ein Schlüsselpaar über WebCrypto, aber statt `extractable: false` (was die Spezifikation empfiehlt und was ein echter Hardware-Authenticator tut), muss ich `extractable: true` verwenden, um den Schlüssel verschlüsseln und in meine eigene Sync-Datenbank schieben zu können:

```js
const keyPair = await crypto.subtle.generateKey(
  { name: "ECDSA", namedCurve: "P-256" },
  true, // extractable: true, weil Synchronisierung sonst unmöglich ist
  ["sign", "verify"]
);
```

Das ist genau derselbe Kompromiss, den (soweit ich das aus ihren öffentlichen Materialien verstehe) Bitwarden und 1Password in ihren Passkey-Implementierungen eingehen: Sie nennen es "software-backed passkeys", im Gegensatz zu "hardware-backed", und schreiben ausdrücklich, dass das ein niedrigeres Sicherheitsniveau ist als ein Schlüssel, der in einer Secure Enclave oder einem TPM eingeschlossen ist. Der Komfort der Synchronisierung kostet einen echten Rückgang der Garantien, die die Spezifikation bietet. Das ist kein Implementierungsfehler, das ist eine grundlegende architektonische Entscheidung, und wer "Passkeys in der Cloud" als identisch mit einem Hardware-Schlüssel bewirbt, lügt ein bisschen durch Unterlassung.

Mein aktueller Plan ist, den privaten Schlüssel lokal mit einem aus einem Master-Passwort abgeleiteten Schlüssel zu verschlüsseln (so etwas wie PBKDF2 oder Argon2 zum Strecken), bevor überhaupt etwas in die Synchronisierung geht, damit der Server den Schlüssel nie im Klartext sieht. Aber das bleibt trotzdem eine Software-Lösung mit dem ganzen Gepäck, das das mit sich bringt: Wenn jemand das Master-Passwort knackt und Zugriff auf die verschlüsselte Datenbank bekommt, ist das Spiel vorbei. Ein Hardware-Schlüssel hat dieses Problem nicht, weil er sich überhaupt nicht aus der Ferne "wiederherstellen" lässt.

## FAQ

**Haben Browser irgendeine offizielle API für Passwort-Manager zur Handhabung von WebAuthn?**
Es gibt keine dedizierte API wie `chrome.webAuthn` für Erweiterungen. Jeder Passwort-Manager, den ich kenne, macht dasselbe wie oben beschrieben: Er tauscht `navigator.credentials` über ein injiziertes Skript aus, das in der Hauptwelt der Seite läuft.

**Ist das konform mit den Richtlinien der Erweiterungs-Stores?**
Das Verändern des Seitenverhaltens über ein Content-Script ist eine legale, verbreitete Technik (so funktionieren auch viele Werbeblocker oder Seitenübersetzer), also ist es an sich kein Problem. Man muss dem Nutzer aber klar mitteilen, was die Erweiterung tut, und darf nichts still und heimlich ohne seine Zustimmung abfangen.

**Was ist der Unterschied zwischen einem "software-backed" und einem "hardware-backed" Passkey?**
Hardware-backed heißt, der private Schlüssel entsteht und lebt ausschließlich in einem dedizierten Modul (Secure Enclave, TPM, Hardware-Schlüssel) und lässt sich physisch nicht exportieren. Software-backed heißt, der Schlüssel existiert als verschlüsselte Daten, die theoretisch wiederhergestellt werden könnten, wenn jemand die Verschlüsselung oder das Master-Passwort knackt. Das zweite ist bequemer für die Synchronisierung, hat aber ein schwächeres Bedrohungsmodell.

**Warum ist `run_at: document_start` so wichtig?**
Weil die Seite sich gleich nach dem Laden eine Referenz auf das originale `navigator.credentials` sichern kann, bevor die Erweiterung überhaupt etwas austauschen kann. Kommt der Austausch zu spät, benutzt die Seite trotzdem den alten Handle, und dein Abfangen greift nie.

**Planst du, das zu veröffentlichen oder den Code zu teilen?**
Im Moment ist das ein Projekt für den eigenen Gebrauch und zum Lernen, also gibt es noch kein öffentliches Repo und keinen Termin. Sobald es einen Stand erreicht, den ich für solide genug halte, damit jemand anderes es sicher nutzen kann, schreibe ich dazu bestimmt einen eigenen Beitrag.

## Zusammenfassung

Und das war's für heute! Kurz gesagt: WebAuthn sieht von der API-Seite nach zwei Funktionen aus, aber darunter steckt eine ganze Choreografie aus CBOR, Origins und Vertrauen in den Authenticator. Eine Browser-Erweiterung kann sich nur einklinken, indem sie `navigator.credentials` in der Hauptwelt der Seite austauscht, mit einem tückischen Injektions-Timing. Und wenn du Schlüssel zwischen Geräten synchronisieren willst, musst du bewusst vom Modell "der Schlüssel verlässt das Gerät nie" auf das Modell "der Schlüssel ist verschlüsselt, aber theoretisch wiederherstellbar" umsteigen, und es gibt keine magische Lösung, die dir beides gleichzeitig gibt.

Und jetzt die Ironie der ganzen Sache: Ich habe das gebaut, weil ich die Abhängigkeit von Passwort-Managern anderer Firmen loswerden und ein eigenes, von mir kontrolliertes Ding haben wollte. Nach drei Abenden komme ich zu dem Schluss, dass der einzige Weg, meinen Vault so sicher wie Bitwarden zu machen, im Grunde darin besteht, die Hälfte der architektonischen Entscheidungen, die Bitwarden schon getroffen hat, neu zu schreiben, nur schlechter, weil ich das allein und nach Feierabend mache. Unabhängigkeit bedeutet manchmal einfach, dieselben Kompromisse neu zu entdecken, die jemand anderes schon längst entdeckt und in seiner technischen Dokumentation beschrieben hat, xd.
