## Introduction

Hey! It started with the usual kind of annoyance. I log in somewhere with a passkey, the browser asks which password manager should handle it, I pick one, I wait, something breaks, I try again from my phone, I scan a QR code, nothing. Try again. Damn it. After the third session like this in one week I thought: this isn't a technology that's allowed to work "most of the time". It has to work every time, because it's the login. So instead of cursing at someone else's product one more time, I opened an empty folder and started writing my own.

That's how passkey-vault was born. This post isn't a changelog and it isn't a step by step tutorial. It's the thing nobody tells you before you actually sit down with WebAuthn: that the demo on the vendor's docs page and a real implementation are two different worlds, and that most of the hard decisions in this project weren't technical at all, they were founder decisions.

You get three things:

1. **what actually hurts in WebAuthn** once you stop copying the docs example and start building something that has to survive contact with real users,
2. **what decisions I had to make as a founder, not a programmer**: what to skip at launch, who to trust, what to build myself versus buy,
3. **when building your own passkey manager is a bad idea**, because honestly, most of the time it is.

The iOS app that came out of this is a topic for its own post. Here I'm staying with the engine itself and the process of getting there.

## What passkey-vault actually is

In short: a passkey manager, meaning a relying party implementation and server side storage that handles registration and login with passkeys per WebAuthn and FIDO2, plus a sync layer so the same user can log in from several devices without scanning a QR code from scratch every time. Sounds like one sentence. In practice it's about twenty smaller decisions, each with security consequences if you get even one of them wrong.

Before anyone asks: no, this isn't "another Bitwarden". It started as a project to understand the protocol well enough that I could trust my own implementation more than someone else's black box, and along the way it started looking like something that could be a standalone product. More on that in the founder decisions section.

## Problem one: the docs demo lies by omission

Every WebAuthn tutorial looks roughly like this:

```javascript
const credential = await navigator.credentials.create({
  publicKey: {
    challenge: new Uint8Array(32),
    rp: { name: "passkey-vault", id: "passkey-vault.example" },
    user: { id: userId, name: email, displayName: email },
    pubKeyCredParams: [{ type: "public-key", alg: -7 }],
  },
});
```

Nice, short, works on localhost in the demo. The problem starts the moment `rp.id` has to exactly match the registrable domain the site is served from, not just any subdomain you feel like. You have `app.passkey-vault.com` and `api.passkey-vault.com` and want a credential to work on both? You have to deliberately set `rp.id` to the shared suffix, not copy whatever happened to work locally. Change the production domain later? Every registered credential stops matching, because it's bound to the origin permanently. That's not a bug to fix, it's a property of the protocol that the demo never mentions, because the demo never changes domains.

The second thing that only hurts once you're in the trenches: testing locally requires either `https://localhost` or a virtual authenticator through Chrome DevTools, because the browser refuses WebAuthn over plain HTTP outside the localhost exception. My first attempt at integration tests mocked the entire `navigator.credentials` object. It quickly turned out the mock misses half of the real failures, because a real authenticator has its own quirks: some hardware keys don't support discoverable credentials, some platform implementations cache state between attempts so two consecutive tests in the same CI run see different things. I eventually switched to a virtual authenticator through the Chrome DevTools Protocol, and only then did the tests start catching something real.

## Problem two: what you actually store in the database

This is where people get it wrong most often, myself included at the start. The private key NEVER leaves the user's authenticator, so the server never sees it and never stores it. What actually lands in your database is: the `credentialId`, the public key, the signature counter (`signCount`), the `backup eligible` and `backup state` flags, and optionally attestation metadata. Sounds harmless until you ask which of those is actually sensitive.

The answer: `credentialId` isn't a secret by itself, but it's an identifier that should be treated like personal data, because it ties a specific user to a specific device. The signature counter is your only line of defense against a cloned hardware authenticator: if the counter on the next login is lower than or equal to the previous one, that's a signal someone cloned the key material and the login should fail. The problem is that passkeys synced through the cloud (iCloud Keychain, Google Password Manager) in practice often report `signCount` as zero on every login, because the counter stops making sense once the same credential lives on multiple devices at once. So the "counter must increase" logic breaks exactly for the case that was supposed to be the most convenient for the user. I had to split verification into two modes: strict for hardware keys with a real counter, lenient for credentials marked backup eligible, where a zero counter is normal, not an alarm.

## Problem three: username-less login, which needed redesigning twice

Discoverable credentials, meaning passkeys the browser can suggest on its own without typing a login, are the number one selling point of passkeys. And rightly so, the UX is better. But implementing it properly requires the server to generate a login challenge WITHOUT knowing the user's identity, because by definition you don't know it yet. My first version of the login endpoint carried a quiet assumption: know the user first, then generate the options. Worked fine for login with a username, broke immediately for a "log in with passkey" button with no email field.

I had to rebuild it into a two step flow: an endpoint that generates options with zero user context, plus a verification endpoint that only after receiving the authenticator's response looks up the user by the `credentialId` returned in that response. Simple to describe in one sentence, but it's exactly the kind of change where you have to rewrite server side validation, because the quiet assumption used to be that the session carries identity. Here identity arrives at the end, not at the start.

## Where the phone comes in: syncing across devices

The biggest real problem for me wasn't cryptographic, it was distributional: how do you make sure a passkey registered on a laptop actually works on a phone without registering from scratch every time. The platform answer is hybrid transport, meaning logging in from a phone into a browser on a different device through a QR code with Bluetooth as the proximity check (caBLE), or full sync through a system provider, iCloud Keychain on Apple's side, Google Password Manager on Android's.

This is exactly where the iOS app topic starts: credential provider extension, integration with system Autofill, the whole on-device UX piece. That's a separate, meaty story, so I'm covering it in the next post. For now remember just one thing: the decision to support hybrid transport at all instead of requiring registration on every device separately was a product decision, not a technical one, and I only made it after my own MVP annoyed me by forcing me to register from scratch on every device.

## Decisions I made as a founder, not as a programmer

Here's the part nobody writes in WebAuthn documentation, because documentation doesn't know you're building a product, not a cryptography exercise.

**What to build yourself versus trust to a library.** I left the actual signature cryptography and verification to a library, because writing your own CBOR and COSE implementation from scratch is exactly the kind of work where a mistake costs more than the time it saves. But the storage logic, the data model, the signature counter policy and the whole registration and login flow I wrote myself, because that's where a product's differentiating value lives, not something to outsource.

**When to stop chasing attestation.** WebAuthn supports attestation, a cryptographic proof that a given credential comes from a specific, certified hardware key model. Sounds like something you obviously have to verify. The problem: verifying attestation requires maintaining and updating vendor metadata (the FIDO Metadata Service), which is a job in itself, and meanwhile most real users log in with a platform passkey, not a certified hardware key, so attestation comes back as `none` anyway. I dropped strict attestation verification for launch and wrote it down as a deliberate debt, not an oversight. That's the difference between an MVP and negligence: one is documented and justified, the other just surprises you later.

**Why build this yourself at all when Bitwarden and 1Password already have it.** Because I wanted a product where I understand every line responsible for my future users' login security, instead of integrating with someone else's SDK and hoping its trust model matches mine. It's a decision that's easy to mistake for "not invented here" syndrome. Honestly, part of it is exactly that syndrome. But part of it is a real calculation: if passkeys are going to be the foundation of the product, I'd rather understand that foundation from the inside.

## When building your own passkey manager does NOT make sense

Fair, in the other direction, because this post is easy to read as pushing everyone toward the same madness. Don't build your own passkey manager if:

- **passkeys are just one of several login methods for you**, not the foundation of the product. Then integrating with a ready made provider (Clerk, Auth0, WorkOS, whatever) costs you a day, while your own implementation costs months and exposes you to security bugs a ready made provider has already caught.
- **you don't have the time budget to keep up with an evolving standard.** WebAuthn and FIDO2 keep changing, new extensions like PRF are still maturing in browser support, and someone has to track it.
- **nobody on your team enjoys reading cryptography specs for fun.** Seriously. This isn't a project you build once and forget, it's a project that needs someone who will keep tending it.

If none of those three points apply to you, meaning passkeys are the core of what you're building, you have the time to maintain it, and someone on the team genuinely enjoys it, then building your own starts to make sense. For me all three conditions held. That doesn't mean they will for you.

## What came out of it

Passkey-vault works: it handles registration, username-less login, and basic sync through hybrid transport. It doesn't yet handle full attestation verification, and that's deliberately deferred, not forgotten. The biggest lesson from the whole process isn't about cryptography, it's about how many decisions that look technical are actually product decisions in disguise: what to skip, who to trust, who you're even building this for.

## FAQ

**How is a passkey different from a regular password in terms of what the server holds?**
The server never sees or stores the private key, that stays in the user's authenticator. What lands on the server side is only: the credential identifier, the public key, the signature counter, and the backup flags. That's a fundamentally different threat model than a database of password hashes, because even a full breach of your database gives an attacker nothing they could log in with.

**Is building your own WebAuthn backend safe if I'm not a cryptography expert?**
Leave the actual cryptography, signature verification, and CBOR parsing to a proven library. What you build yourself is the business logic around it: storage, counter policy, login flow. You can still make security mistakes there, but they're much easier to reason about and test than your own implementation of cryptographic primitives.

**Why is the signature counter sometimes zero on every login?**
Because a passkey synced across devices through the cloud doesn't have a single, monotonically increasing counter by nature, since the same credential is used from multiple places at once. That's normal for credentials marked backup eligible and backup state. The strict "counter must increase" rule only makes sense for hardware keys without sync.

**What about the iOS app, the credential provider, and Autofill integration?**
That's a separate, bigger topic that deserves its own post, because integrating with system Autofill on iOS has a completely different set of problems than the WebAuthn backend. Coming in the next article.

**Does this make sense as a product, or is it just a learning project?**
It started as a project to understand the protocol. Along the way it started looking like something that could be a standalone product, mostly because the frustration I started from is real and affects more people than just me. Whether that actually turns into a product, we'll see. Right now it's a solid engine I understand inside out.
